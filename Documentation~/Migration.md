# Переход с 0.1 на 0.2

1. Сохраните резервную копию проекта и файлов сохранения.
2. Сохраните исходные `.meta` ресурсов и скриптов. Сериализованные поля ResourceDefinition и ResourceAmount сохранили имена; перенос полей идентичности в базовый DefinitionAsset не меняет ID ассетов.
3. Возвращаемые количества и `ResourceAmount.Amount` теперь `long`. Явные `int total = GetTotal(...)` замените на `long` или `var`. Входные целые `int` продолжают передаваться без дополнительного преобразования. Не приводите большие остатки к `int` без проверки диапазона.
4. DTO записывается как версия 2; версия 1 с целыми ресурсами читается. Новая точность по умолчанию 0. Версия 1 не может содержать активные резервы.
5. Если меняете ID или Decimal Places, предварительно выполните `ResourceStateMigration`. Укажите старый ID, новый ResourceDefinition, прежнюю точность и явное округление. Не меняйте точность существующего ресурса без преобразования количеств, в том числе в активных операциях.
6. При обновлении Samples удалите прежнюю импортированную копию через Unity и импортируйте новую; не оставляйте два одноимённых sample-assembly. Сохраните собственные изменения отдельно. Локальные сцены Games Factory уже используют единственную копию.
7. Код сторонних интеграций должен ссылаться на нужную сборку. Ядро по-прежнему называется `EasyResources.Runtime`; основные вызовы Add / CanAfford / TrySpend / TryReserve и Commit / Cancel сохранены.

## Правила, которые стоит учитывать

- Перевод и обмен проверяют **исходный доступный запас**, затем итоговые лимиты. Получаемый в той же операции ресурс не оплачивает её вход.
- `ResourceOperationContext` задаёт причину, владельца и время для диагностики. Это описание операции, а не доказательство полномочий пользователя.
- Любая запись из уведомления в участвующий кошелёк отклоняется. Для последующего действия используйте очередь и обработайте её после возврата из события.
- Резерв существует до явного Commit / Cancel / ExpireReservations или уничтожения хранилища. Часы не опрашиваются автоматически.
- Сохранение активных операций включается явно. После восстановления старые дескрипторы и старые scopes не могут отменить новые операции. Вновь свяжите управляющие объекты с сохранёнными reservation ID.
- Валюты, предметы и прогрессия имеют разные состояния. Inventory не заменяет ResourceStore; уникальному мечу нужна identity экземпляра, обычному золоту — количество.
- BigInteger выделяет память. Сетевые DTO, подготовка стоимости, создание объектов, сохранение и изменение подписок также не являются операциями с гарантией отсутствия аллокаций.

Миграция кошелька не меняет произвольный внешний JSON автоматически. Если игра хранит замороженные стоимости в ProductionQueueState / ResearchState / ResourceDeliveryState, преобразуйте их через `ResourceStateMigration.MigrateRows` с теми же правилами **до** связывания с резервами; иначе FromState намеренно отклонит несовпадение оплаты.
